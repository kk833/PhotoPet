## 二、架构

```
┌─ 表现层（Qt）───────────────────────────────────────────┐
│  main.py        PetWindow / 气泡 / 纸质卡片 / 托盘 / 菜单  │
│  chat_window.py 对话窗口 + API 设置窗口                   │
└───────────────────────┬─────────────────────────────────┘
                        │  跨线程只用 Qt 信号（唯一通道）
┌───────────────────────▼─────────────────────────────────┐
│ 业务层（纯 Python，无 Qt，可单测）                          │
│   pet_status 养成    pet_work 陪伴计时   pet_profile 档案   │
│   pet_schedule 日程  pet_task 待办       pet_lunar 农历     │
│   pet_memory 记忆    pet_weather 天气    pet_ai 对话/语音    │
│   ai_tools 工具注册表  pet_web 抓网页    pet_import 读文件    │
└───────────────────────┬─────────────────────────────────┘
                        │
              用户数据目录（纯文本：JSON / Markdown）
              schedule.json · tasks.json · MEMORY.md · weather.json
```

**一条贯穿的设计约束**：业务层不 import Qt。所以日期计算、重复规则、农历换算、
匹配算法这些最容易出错的逻辑，全都能脱离界面跑测试 —— 250+ 用例里绝大多数是这么来的。

## 三、几个真解决过的问题

### 1. 农历换算：自研 + 穷举验证（顺带规避了许可问题）

"生日按农历过"需要把农历日期换算成公历，而**农历生日对应的公历日每年都变**
（农历十月十九 = 2025-12-08 / 2026-11-27 / 2027-11-16）。

- 最省事的是 `pip install lunardate`，但它在 PyPI 上标 MIT、**源码头部却写着
  derived from the GPLv2 `lunar` project** —— 本项目是 MIT，抄表或打进 exe 都会污染许可
- 改为用 MIT 的 `borax` **生成数据后内嵌**（数据是天文事实：每年正月初一落在哪天、
  哪个月大哪个月小、哪一年有闰月；编码格式是本项目自己的），发布版因此**零新增依赖**
- **验证方式**：把 1900-01-31 ~ 2099-12-31 共 **73,019 天逐日**与参考实现比对，
  再加每个农历日的月长上下界检查 —— **0 处不符**；并用第二种独立实现交叉验证未来 6 年

### 2. 让大模型能"上网"，但挡住它读你家的路由器

给 LLM 加了 `read_url` 工具（聊天里发链接，它读进来再回答）。**但工具的地址是模型给的，
不可信** —— 它可能被提示词带偏去读 `http://192.168.1.1/`、`http://localhost:8000/`
这类内网地址，等于把用户的路由器、公司内网暴露给外部模型试探。

做法：抓取前解析域名，**检查所有**解析结果的 IP 都是公网地址才放行。
只查第一个 IP 的话，一个域名同时解析到公网和内网就能绕过去。
实测挡住 `localhost` / `127.0.0.1` / `192.168.x` / `10.x` / `169.254.169.254`
（云服务器元数据地址，能偷到密钥那种）/ `file://`。

### 3. 流式对话 + "想出一句说一句"

模型回复是流式返回的，但语音是**排队逐句念**的 —— 等整段生成完再读，首字要等好几秒。

做法：把 token 流按**句末标点**切成完整句子，凑够一句就先合成朗读。
两个坑：
- **不能按逗号切**（"你好，我是小王"切成两句听着很怪），但一句话超过 32 字要按逗号兜底，
  否则一句长话又要等很久

- 语音播放器原本**新句子会直接掐掉上一句**（单句对话看不出来），必须加播放队列

结果是首字延迟从"整段生成完（约 2 秒）"降到"第一句出来"。

### 4. 逆向一个"藏起来"的网页列表

高校就业网的宣讲会列表**不是普通 HTML** —— CMS 把内容 base64 + zlib 压缩后塞在
`<script>` 里（国内 CMS 常见的 "jz" 混淆）。

解法注释里写着 `去掉前 77 字符 → base64 解码 → 去掉前 40 字符`，照抄**解出来是乱码** ——
因为**那两个数字不是固定的**，它对应前缀标记的长度，服务端不同变体不一样。
改成用正则找真正的 base64 段、解码后从第一个 `<` 开始切，从此不依赖任何魔数。

### 5. 自绘"一页纸"：横线要对齐字行

档案卡和日程卡做成横线信纸的质感（纸底渐变 + 噪点平铺 + 软阴影，噪点程序生成，
不需要贴图文件）。第一版横线按固定间距平铺，**文字骑在两条线中间**，一眼就是假的。

改成从正文的**实际行高**（`QFontMetrics.lineSpacing()`）和首行位置反推线位 ——
注意不是 `height()`，那个值不一样，用错了线会整体偏移。

## 四、工程取舍（这部分比"用了什么技术"更能说明问题）

| 取舍 | 决定 | 理由 |
|---|---|---|
| 记忆用向量库吗 | **不用**，就三个 Markdown 文件 | 桌宠这点记忆量（几千字）全文本注入准确率 100%、零依赖零成本；向量检索在这个量级是杀鸡用牛刀 |
| 给 LLM 开文件读写工具吗 | **不开** | 一旦模型能写文件，路径沙箱、用户确认、误删防护都得跟上，而桌宠不需要这些能力 —— 不开就没有这些风险 |
| 宣讲会要不要智能筛选 | **不筛**，只过滤"日期在将来" | 漏掉一场 = 少一个机会；多看几场不相关的 = 浪费几秒。代价完全不对称 |
| 日期过滤交给谁 | **代码**，不交给模型 | 模型筛是概率的（实测同一页面两次调用：15 条 / 0 条），代码筛是确定的 |
| 记忆怎么写 | 文件名**由代码写死** | 模型只能提供"记什么"、不能指定路径，从设计上消除路径穿越 |
| 什么时候可以开口说话 | **按事由**，不按时间 | 用户明确反对定时闲聊。口时机只有三种：互动、久坐提醒、**有事要办**（任务逾期/快下雨了） |

## 五、测试抓出来的问题（这类 bug 靠肉眼是发现不了的）

- **PyQt6 的虚拟方法里抛异常会让进程静默 abort** —— 没有回溯、退出码 127，
  看起来像"命令不存在"。原因是搬代码时漏了一个 `QRectF` 的 import。
  排查方法：把 `paintEvent` 包一层 try/except 写日志文件
- **`save()` 每次刷新 `last_seen`**，而它是"上次退出时间" —— 结果"开机补报错过了什么"
  永远查不出东西
- **提醒窗口写成 `now < when`**，导致正好在整点那一分钟启动时永远不提醒
- **模糊匹配门槛太松**：中文里「公司」几乎每个标题都有，于是拿"不存在的公司"去查，
  会回"有 32 条都对得上"。改成相对阈值（公共子串占较短那方的一半）
- **提前量参数没传下去**：注释写着"宣讲会提前 30 分钟提醒"，实际下游拿不到、全退回 15 分钟

## 六、构建与分发

- **PyInstaller onedir 打包**：体积控制在 ~110MB。为什么不是 onefile ——
  桌宠是常驻 + 开机自启的，onefile 每次启动都要解压 80MB，每次开机都慢几秒、
  杀软每次都扫一遍
- **CI**：GitHub Actions 在 Windows 上构建，推 `v*` 标签自动发布 Release
- **两个打包目标**：运行时版（~110MB）和创作版（含抠图模型，~500MB）分开发布 ——
  把 1GB 的抠图依赖塞进给普通用户的包里没有意义
